# Cloudflare Pages website security

This repository now contains a separate React/Vite marketing and download site in `website/`. It does not share the Electron renderer entry or the Electron `dist/` output. The Pages project serves `website-dist/`; Pages Functions are discovered from the repository-root `functions/` directory.

## Cloudflare Pages project

- [ ] Connect only the intended Ty-Code Git repository and protect its production branch.
- [ ] Set the Pages project root to the repository root so Pages discovers `functions/` and `wrangler.jsonc`.
- [ ] Set the build command to `npm run build:website` and the build output directory to `website-dist`.
- [ ] Use the repository's locked Node/npm toolchain. The website reuses existing exact-pinned React/Vite packages; do not install dependencies with `npm install` in CI.
- [ ] Confirm the deployed `website-dist/_headers` file is parsed as Pages configuration (it is not meant to be a browsable asset) and inspect response headers on `/`, `/icon.svg`, and a deep route.
- [ ] Confirm `/api/release` and `/api/pageview` route to Functions and that Function responses include their own security headers. Cloudflare Pages `_headers` rules do not apply to responses generated by Functions.
- [ ] Add the production custom domain only after DNS, redirects, and the final response headers have been verified.

## HTTP security headers

`website/public/_headers` sets one policy for static files:

- CSP uses `default-src 'self'`, `script-src 'self'`, `style-src 'self'`, `connect-src 'self'`, `frame-ancestors 'none'`, `form-action 'self'`, and `base-uri 'self'`; it also denies objects and permits only the requested image sources. No inline or third-party script/styles are loaded.
- HSTS is `max-age=31536000; includeSubDomains; preload`. Enable it only after every subdomain is HTTPS-ready. Preload enrollment is a separate decision and requires satisfying the current browser preload requirements; the header alone does not enroll a domain.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, and the requested `Permissions-Policy` are set.

Pages Function handlers independently set a restrictive JSON CSP, HSTS, nosniff, DENY, referrer, permissions, and same-origin resource policy. Review response headers after deployment because `_headers` does not apply to Function responses.

The site fetches release metadata and submits the optional page-view event only through same-origin `/api/*` endpoints. This preserves `connect-src 'self'`. There are no external CSS/JS resources; if a future change adds one, prefer self-hosting. If an external CSS/JS resource is unavoidable, pin its version and include a correct SRI `integrity` and `crossorigin` attribute, then explicitly review CSP and the supply-chain risk.

### Bot Fight Mode / challenge compatibility

The requested strict `script-src 'self'` does not allow arbitrary challenge scripts. Test Cloudflare Bot Fight Mode and any injected JavaScript challenges on a staging hostname before enabling them for production traffic. Do not weaken CSP with `unsafe-inline` just to silence a challenge error. If the challenge cannot operate within the policy, use an edge bot/WAF control that does not require loosening the site policy and document the final exception before rollout.

## WAF and bot protection

- [ ] In Cloudflare **Security → WAF → Managed rules**, enable Cloudflare Managed Rules and the OWASP Core Ruleset (Cloudflare’s implementation of the OWASP ModSecurity Core Rule Set; it is not a literal OWASP Top 10 ruleset mapping).
- [ ] Start with conservative actions (log or managed challenge where appropriate); review security events and false positives before applying blocking overrides. Verify both HTML access and GitHub release downloads from each supported platform.
- [ ] Enable Bot Fight Mode under **Security → Settings → Bot traffic** after staging tests. Confirm normal browsers, screen readers, legitimate package downloads, and the strict CSP continue working.
- [ ] Set rate limiting for `/api/release` and `/api/pageview` if available on the selected plan. The release Function only allows a fixed upstream GitHub URL and does not accept a caller-supplied URL, owner, repository, or tag.
- [ ] Monitor the Pages Functions error/invocation metrics; the release check caches successful results briefly at the edge, while missing/error results are not cached.

Cloudflare WAF, Bot Fight Mode, and rate limits are dashboard/plan settings. Committing `_headers` does not enable those services.

## SSL/TLS

- [ ] Set **SSL/TLS → Overview → Encryption mode** to **Full (strict)**.
- [ ] For Cloudflare Pages, verify the custom domain certificate is active and HTTPS works before adding HSTS. If an external origin is introduced, its certificate must be current, publicly trusted or Cloudflare Origin CA, and valid for the origin hostname.
- [ ] Enable **Always Use HTTPS** or an equivalent HTTPS redirect at the edge; test HTTP → HTTPS and custom-domain canonicalization.
- [ ] Add `includeSubDomains` only when every covered hostname is HTTPS-capable. Treat `preload` as an explicit long-term domain decision, not a dashboard toggle to enable casually.
- [ ] Verify HSTS, CSP, and all required response headers with a real production request after deployment.

## Release integrity and downloads

The `/api/release` Pages Function is pinned to `ty-code/ty-code`. It requests only the GitHub latest-release endpoint and official release assets, validates the release tag and official URLs, bounds the checksum manifest to 256 KiB, and exposes only known Ty-Code installers whose exact filenames have a 64-hex entry in `SHA256SUMS.txt`. It never constructs an asset URL from browser-provided input. The browser validates the response again before rendering a Download link.

- [ ] Publish a public stable GitHub release with `SHA256SUMS.txt` before expecting download links to appear. The configured GitHub API returned 404 when this site was implemented, so the site deliberately shows a missing-release state rather than placeholder installers/checksums.
- [ ] Verify each published filename is byte-for-byte identical to its SHA-256 manifest filename. The release workflow currently generates the manifest from release artifacts.
- [ ] Verify download URLs resolve only to the official GitHub release path and check a downloaded package against the shown SHA-256.
- [ ] Treat the checksum as an integrity comparison, not a digital signature or independent proof of publisher identity. Continue to sign and notarize release binaries through the existing release workflow.

## Website analytics and privacy

The website uses a deliberately small same-origin aggregate counter endpoint; it does not load Cloudflare Web Analytics, Plausible, or any external analytics JavaScript. Cloudflare's published Web Analytics materials describe cookie-free collection, but do not establish DNT compliance. Therefore this implementation gates its own event rather than assuming a provider honors DNT.

When `navigator.doNotTrack === '1'` or `navigator.globalPrivacyControl === true`, the browser does not send the event. The Pages Function also drops requests with `DNT: 1` or `Sec-GPC: 1`, validates same-origin `Origin`, accepts only the body `{"event":"page_view"}`, and writes only fixed `website` / `page_view` labels and count to the optional Workers Analytics Engine binding. It does not write IP addresses, User-Agent, referrer, query strings, paths, cookies, session IDs, or persistent identifiers in application code. No cookie or browser storage is set. If the binding is absent, website delivery continues and no event is stored.

- [ ] If enabling the Analytics Engine binding, attach the `SITE_ANALYTICS` binding to dataset `ty_code_site` in both production and preview Pages environments; redeploy and confirm aggregate-only values.
- [ ] Set and review Analytics Engine retention/access according to the current Cloudflare account plan and organizational privacy requirements; the application does not promise a retention period that has not been configured.
- [ ] If adopting Cloudflare Web Analytics or another provider later, first verify DNT and Global Privacy Control suppression, cookie/storage behavior, provider retention/IP/log handling, CSP requirements, and SRI/versioning. Update this page and the website privacy notice before enabling it.
- [ ] Keep marketing-site analytics separate from Ty-Code desktop telemetry. The desktop app remains opt-in/local-only and has no telemetry transmission path in the current build; enabling website analytics does not grant consent for app telemetry.
